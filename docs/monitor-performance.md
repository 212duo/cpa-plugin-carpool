# 请求监控性能验证（2026-10-17）

当前实现的记录缓存为 10 秒，汇总缓存为 30 秒；缓存绑定认证后的 Key hash、数据库文件身份、配置版本与筛选条件。汇总缓存可在不同列表长度之间复用，但不能跨 Key / 状态 / 时间范围复用。整页缓存不能延长旧汇总的有效期。

## 环境与方法

- 本机 Intel Core i5-13600KF，20 个逻辑处理器，约 32 GB 内存；Windows / amd64，本地 SSD / NTFS。Go 1.26.0、modernc SQLite 1.34.4。
- 1,000,000 条基础记录，100 个独立 Key，每个 Key 10,000 条、8 个模型；数据覆盖最近 6 天，查询最近 7 天、最近 100 条。基础库约 528 MiB，建索引及重用后约 609 MiB。另有持续写入测试产生的记录。
- 使用 loopback HTTP 压测服务，调用实际插件监控处理函数；包含认证、JSON 编解码、缓存和真实 SQLite 查询。未包含 CPA 的 C ABI 跨界调用、TLS、外部网络或真实模型请求，另以真实 CPA 宿主做功能联调。
- 对照实现取自 `f279e06`，保留在 `monitor_baseline_test.go`，仍使用三条数据查询且不缓存；它只用于测试，不编译进插件。
- 所有成功响应逐条验证当前 Key 的调用数、标准化输入 / 缓存量，以及模型与请求列表中的 Key 专属模型前缀，同时检查私密字段哨兵没有出现在响应中。
- `数据 SQL` 统计真正发起的数据查询，不含初始化的表结构检查、测试库准备与后台测试写入。

优化后的各场景均无请求失败、跨 Key 数据混入或统计错误。无索引的旧实现对照在 8 并发下，24 次请求全部触发原有 3 秒期限；这不是新实现的失败。无索引的 20 个 Key 顺序预热耗时超过记录 TTL，因此预热后并发阶段正常触发 8 条近期记录查询，没有重新扫描汇总。只有有复合索引的场景验证了 50 个不同 Key 同时冷查询。

35 秒持续场景以 50 客户端、20 个活跃 Key，在 0 / 10 / 20 / 30 秒各发起一轮请求，累计 200 次；同时以 10 条 / 秒向另一个 Key 写入记录，实际完成 349 次写入，写入错误为 0。这个独立写入 Key 的数据没有进入任何买家响应。整个阶段执行 67 条监控数据 SQL；同样 200 次请求若逐次执行旧版三查询，会发起 600 条数据 SQL。

该持续场景进程累计 CPU 时间 2.53 秒 / 墙钟时间 35.00 秒，约为单个逻辑核的 7.2%。此处进程同时运行 HTTP 服务、压测客户端、响应校验与测试写入，不能视作生产插件的净增 CPU 占用。极限吞吐阶段会主动占满可用 CPU，也不代表正常每 10 秒刷新时的消耗。

Windows 原始报告没有采集工作集峰值，`PeakRSSMiB: 0` 表示未采集；Go 堆大小不等于整个插件或 CPA 的内存需求。两级缓存的 20 MiB 是 JSON 数据上限，不含 Go、SQLite、HTTP 与在途请求的额外内存。

原始结果：[monitor-2026-10-17-windows.json](benchmarks/monitor-2026-10-17-windows.json)。

## 隔离与并发回归

自动化测试覆盖：同上游账号、同席位的不同 Key 不互用缓存；范围 / 状态 / 列表长度正确隔离；相同查询合并；缓存字节互不共享可写存储；LRU / 字节容量 / TTL 上限；记录缓存不延长汇总；错误不缓存；配置失效、Key 撤销 / 到期与在途取消；数据库删除 / 替换；超过 50 个模型时完整总量及加权平均耗时；索引脚本幂等且查询计划实际使用复合索引。

Linux 的 `go test -race`、页面测试与真实 CPA v8.0.30 联调配合验证这些行为。CI 每次增加 100,000 条数据的并发回归，并上传 JSON 报告；百万条完整压测显式执行。

## 复现

默认完整测试会创建临时合成数据库；请预留约 1 GB 磁盘空间。Linux / macOS：

```bash
CARPOOL_MONITOR_STRESS=1 CARPOOL_MONITOR_STRESS_SUSTAINED=1 \
  go test -run '^TestMonitorLargeDataLoad$' -count=1 -timeout 15m -v .
```

Windows PowerShell：

```powershell
$env:CARPOOL_MONITOR_STRESS='1'
$env:CARPOOL_MONITOR_STRESS_SUSTAINED='1'
go test -run '^TestMonitorLargeDataLoad$' -count=1 -timeout 15m -v .
```

可选环境变量：`CARPOOL_MONITOR_STRESS_ROWS`（至少 10,000，且为 100 的倍数）、`CARPOOL_MONITOR_STRESS_DB`（复用合成测试库）、`CARPOOL_MONITOR_STRESS_REPORT`（JSON 报告路径）。指定测试库时，程序拒绝修改缺少合成数据标记或参数不匹配的数据库；不要指向真实数据。可重复执行的生成库会保留上次持续写入的附加记录，原始 100 个 Key 的数据量保持不变。

## 部署边界

大库先在 Manager Plus 的数据库写入端执行 [usage-monitor-index.sql](../scripts/usage-monitor-index.sql)。插件保持只读，不会替管理员自动建索引。有索引和无索引的冷查询差别明显，不能将热缓存结果用作无索引、大量新 Key 首次进入时的保证。

上面的耗时属于这台机器与这个合成负载。生产环境的磁盘、CPU、其他负载、数据保留时长、单 Key 记录量和模型数量都会影响结果；尤其不代表小规格服务器也能达到相同吞吐。需要在部署环境重复该负载评估，而不是照搬本机的资源百分比。
